# 献立おまかせLINEボット — 要件定義（v0.2 / 2026-10-24）

## 1. 目的・背景

毎日の「何を食べよう」「何を作ろう」と考えること自体に疲れている（選択疲れ）。
レシピは Notion に貯めてあるが、その中から選ぶのにもエネルギーを使う。

このツールは、**自分の一軍レシピ（Notion）の中から、その日のコンディションと気分に合う献立を1セット（余裕がある日は2択）だけ提案する**ことで、献立を決める負担をなくす。

### 設計の考え方

- **選択肢を増やさない**: 提案は Notion に登録済みのレシピからのみ行う。AIに新しいレシピを考えさせない。
- **選択肢は最大2つまで**: 候補を並べると、また選ぶことになる。通常は1セットのみ提案し、引き直しは2回までにする。例外は「余裕あり」の日で、「作ってみたい」セットと一軍セットの2択にする（4.4参照）。2択までなら選ぶ負担は小さいと判断した。
- **自分から聞いたときだけ動く**: 毎日の定時通知は、いずれ見なくなるので行わない。自分がLINEで話しかけたときに起動する。例外は、後述する「作った？」の確認だけ。
- **入力はボタンで**: 状態の回答はクイックリプライのボタンで行う。文字を考えて打つ手間を減らすため。

## 2. 利用者・利用シーン

- 利用者は本人1人。LINEの userId で本人以外のメッセージは無視する。
- 夕方、買い物の前や帰宅後にLINEで「何食べよう」と送る。

## 3. 会話フロー

### 3.1 献立の提案

```
自分：何食べよう
Bot ：今日のコンディションは？   [ヘトヘト] [ふつう] [余裕あり]
自分：[ヘトヘト]
Bot ：気分は？                   [がっつり] [さっぱり] [なんでも]
自分：[がっつり]
Bot ：今日はこれどう？
      🍖 しょうが焼き
      🥗 漬け新玉ねぎ
      （ごはんと一緒に）
      → 手間が少なく、がっつり食べられます
      [これにする] [別のがいい]
```

一品完結のメインを選んだ場合は、ごはんは付けず、手間の少ない副菜を1品付ける（一品ものは野菜が不足しがちなため）。

```
Bot ：今日はこれどう？
      🍳 究極のレタスチャーハン
      🥬 千切りキャベツ（カット野菜）
      → チャーハンにさっと野菜を添えて
      [これにする] [別のがいい]
```

- **きっかけの言葉**: 「何食べよう」「献立」「ごはん」などを含むメッセージで提案を始める。
- **自由文での入力**: 「疲れたけど肉食べたい」のような自由な文章が来たら、Claude がコンディションと気分に読み替え、ボタンでの質問を省略して提案する。
- **[別のがいい]**: 直前の提案を除いて、もう一度提案する。2回まで。3回目は「今日はこの中から決めちゃおう」と、これまでの提案を並べて終える。
- **[これにする]**: 献立ログに「確認待ち」として記録し、「いってらっしゃい！」と返す。

### 3.2 「作った？」の確認（後追い）

```
（[これにする]を押してから約90分後）
Bot ：さっき決めた「しょうが焼き＋漬け新玉ねぎ」、作った？
      [作った] [作ってない]
自分：[作った]
Bot ：おつかれさま！記録しておきました
```

- **[作った]**: 提案したレシピすべての「最後に作った日」に、ボタンを押した日の日付を入れる。献立ログのステータスを「作った」にする。
- **[作ってない]**: レシピは更新しない。献立ログのステータスを「作ってない」にする。
- **返事がない**: 何も更新しない。確認の送信は1回だけで、再送はしない。

### 3.3 「どうだった？」の評価（作ったことないレシピだけ）

[作った]を押した献立に、作ったことないレシピ（評価が「まだ作ってない」または未評価）が含まれていた場合は、続けて評価を聞く。

```
自分：[作った]
Bot ：おつかれさま！記録しておきました
      初めての「ねぎ塩豚バラ炒め」、どうだった？
      [おいしい] [ふつう] [残念]
自分：[おいしい]
Bot ：一軍入り！次から候補に入れておきます
```

- 押したボタンの値を、そのレシピの Notion の「評価」に書き込む。
- **おいしい**: 一軍になり、次から通常の候補に入る。
- **ふつう**: 一軍には入らない。作ったことないレシピの扱いからも外れるので、どの候補にも出なくなる。「まずくはないが、また作りたいとは思わない」レシピとして Notion に記録だけ残す。
- **残念**: 常に除外される（4.2の既存ルールどおり）。
- 返事がない場合は評価を変えない（作ったことないレシピのまま残る）。
- すでに評価があるレシピ（一軍）については聞かない。

## 4. 提案ロジック

### 4.1 献立の形

- **通常**: メイン1品＋副菜1品＋ごはん。ごはんは Notion で管理せず、提案メッセージに「（ごはんと一緒に）」と添えるだけにする。
- **一品完結のメイン**（チャーハン、パスタ、カレー、うどんなど）: 主食を兼ねるため**ごはんは付けない**。ただし一品ものは野菜が不足しがちなので、**副菜は1品付ける**。副菜は手間が「ラク」のものから選ぶ（メインがすでに一皿で完成しているため）。提案メッセージに「ごはんと一緒に」は付けない。
- **買うだけ・切るだけの副菜**: 千切りキャベツ（カット野菜）、ミニトマトなど、Notion にレシピとしては入っていない手間ゼロの野菜も副菜の候補にする。これらはレシピ_DB に「副菜」として行を追加して管理する（5.1参照）。AIが自由に考えた副菜は出さない。

### 4.2 候補の絞り込み（Pythonのルールで行う）

| 条件 | 内容 |
|---|---|
| 一軍 | 評価が「おいしい」のもの |
| コンディション「ヘトヘト」 | 手間が「ラク」のもののみ |
| コンディション「ふつう」 | 手間が「ラク」または「ふつう」 |
| コンディション「余裕あり」 | 手間はすべて対象。一軍セットに加えて、評価が「まだ作ってない」・未評価のもの（＝作ってみたくて保存してあるレシピ）を使った「作ってみたい」セットも作り、2択で提案する（4.4参照） |
| かぶり防止 | 最後に作った日が今日・昨日・一昨日のものは除外する |
| 手間が未入力 | 「ふつう」として扱う |
| 除外 | 評価が「残念」のものは常に除外する。引き直し時は、それまでに提案したものも除外する |

候補が0件になったら、かぶり防止の条件を外して再度絞り込む。

### 4.3 最終選択（Claude）

絞り込んだ候補の一覧と気分（がっつり／さっぱり／なんでも）を Claude に渡し、次の2つを返させる。

- メインと副菜の組み合わせ（候補一覧に含まれるページIDのみ）
- 提案理由（1文）

「余裕あり」の日は、A（作ってみたい）と B（一軍）の2セット分を1回の呼び出しで返させる。

### 4.4 「作ってみたい」と一軍の2択（余裕ありの日だけ）

コンディションが「余裕あり」の日は、次の2セットを並べて提案し、どちらかを選んでもらう。

- **A. 作ってみたいセット**: 未経験のレシピ（評価が「まだ作ってない」または未評価）を1品含むセット。メインが未経験なら副菜は一軍から、副菜が未経験ならメインは一軍から選ぶ。未経験のメインが一品完結なら、ごはんは付けず、副菜は一軍の「ラク」から選ぶ。
- **B. 一軍セット**: 一軍（おいしい）だけで組んだセット。

```
Bot ：今日は余裕あり！どっちにする？

      【A】作ってみない？
      🆕 ねぎ塩豚バラ炒め（まだ作ったことないレシピ）
      🥗 漬け新玉ねぎ
      （ごはんと一緒に）

      【B】いつもの一軍
      🍖 至高の油淋鶏
      🥗 かぼちゃのそぼろ煮
      （ごはんと一緒に）

      [Aにする] [Bにする] [別のがいい]
```

- 未経験のレシピには「🆕」と「まだ作ったことないレシピ」の表示を付ける。
- A と B で同じレシピは使わない。
- [別のがいい]を押すと、A・B とも作り直す（引き直しは2回まで、通常と同じ）。
- 未経験の候補がない場合は、B だけの通常の1セット提案にする。
- 「ヘトヘト」「ふつう」の日は、未経験のレシピを提案せず、通常の1セット提案にする（失敗したくない日に冒険させないため）。
- [Aにする]／[Bにする]を押した後の流れ（献立ログへの記録、「作った？」の確認）は、[これにする]と同じ。

### 4.5 補足

がっつり／さっぱりは、Notion に列を持たず、Claude が料理名から判断する。
Claude の応答が候補外のIDだった場合や、APIエラーの場合は、候補からランダムに選ぶ（理由文なし）。

## 5. データ（Notion）

### 5.1 既存: レシピ_DB（追加する列）

| 列名 | 型 | 値 | 用途 |
|---|---|---|---|
| 手間 | セレクト | ラク／ふつう／がんばる | コンディションでの絞り込み |
| 一品完結 | チェックボックス | — | オンなら主食を兼ねる料理として、ごはんを付けない（副菜は付ける） |
| 最後に作った日 | 日付 | — | かぶり防止。[作った]を押したときだけ更新 |

既存の列（名前・タグ・評価・分類・URL など）は読み取りのみで、変更しない（例外: 3.3の「どうだった？」で評価を書き込む）。

あわせて、買うだけ・切るだけの副菜（千切りキャベツ、ミニトマト など）を、タグ「副菜」・手間「ラク」・評価「おいしい」の行として追加する。品目は本人が決める。
提案メッセージには、レシピの URL 列の値を添える（作るときにすぐ開けるように）。

### 5.2 新規: 献立ログ_DB

| 列名 | 型 | 内容 |
|---|---|---|
| タイトル | タイトル | 例: 「2026-10-22 しょうが焼き＋漬け新玉ねぎ」 |
| レシピ | リレーション（レシピ_DB） | 提案したレシピ |
| 決定日時 | 日付（時刻あり） | [これにする]を押した日時 |
| ステータス | セレクト | 確認待ち／作った／作ってない |
| 確認送信済み | チェックボックス | 「作った？」を送信済みかどうか |

## 6. システム構成

```
LINE アプリ
   │  メッセージ・ボタン操作（Webhook）
   ▼
Webhookサーバー（Python / FastAPI）
   ├─ Notion API … レシピ取得、献立ログ記録、最後に作った日の更新
   ├─ Claude API … 自由文の読み替え、最終選択と理由文
   └─ LINE Messaging API … 返信（reply）

GitHub Actions（30分おきの cron）
   └─ 確認待ちで90分経過したログを探す → LINE に「作った？」を送信（push）
   ※ GitHub の定期実行は混雑時に間引かれ、実際は数時間おきになることがある（2026-10-26〜30 の実測で 2.8〜6.9 時間おき）。
     「作った？」は届けばよく、時刻どおりである必要はないため、この遅れは受け入れる（2026-10-30 決定）。
     Cloud Scheduler でボット本体を30分おきに起こす案は、インスタンスベース課金で月数千円かかる見込みのため見送った
```

- **会話の状態**: サーバーには保存しない。ボタンの postback データに「コンディション」「気分」「これまでに提案したID」を持たせ、サーバーを再起動しても会話が途切れないようにする。
- **デプロイ先**: Webhookサーバーは常時受け付けが必要なため、Google Cloud Run（us-central1、最小0台・最大1台）に置く（2026-10-26 決定）。Render の無料枠は、スリープからの起動に時間がかかり、LINE の Webhook が2秒で打ち切られるため見送った。Cloud Run では、返事のあとも Notion・Claude の処理を続けるため、インスタンスベース課金（`--no-cpu-throttling`）にする。開発中は ngrok でローカルのサーバーを公開する。

### 6.1 ファイル構成（予定）

| ファイル | 役割 |
|---|---|
| `main.py` | FastAPI の Webhook 受け口。署名検証、イベントの振り分け |
| `config.py` | 環境変数の読み込み |
| `recipe.py` | レシピのデータ型（Recipe） |
| `notion_repo.py` | レシピ取得、献立ログの作成・更新、最後に作った日の更新（公式SDKのパッケージ名 `notion_client` と衝突しないよう改名） |
| `cli.py` | LINE なしで提案を試す CLI（`python cli.py ヘトヘト`） |
| `recommender.py` | 候補の絞り込み（ルール）と最終選択の呼び出し |
| `claude_client.py` | 自由文の読み替え、最終選択 |
| `line_messages.py` | クイックリプライ・ボタンなどのメッセージ組み立て、postback データ（会話の状態）の作成 |
| `line_api.py` | LINE の署名検証、返信（reply）、ローディング表示 |
| `followup.py` | GitHub Actions から実行する「作った？」送信スクリプト |
| `tests/` | 絞り込みロジックなどの単体テスト |

## 7. 非機能要件

- **セキュリティ**: LINE の署名（X-Line-Signature）を検証する。`LINE_USER_ID` 以外からのイベントは無視する。秘密情報は `.env` と GitHub Secrets で管理し、コミットしない。
- **応答速度**: ボタンを押してから数秒以内に返信する。
- **LINEの送信数**: 返信（reply）は無料。「作った？」の送信（push）は無料プランの月間上限にカウントされる。1日1回の利用なら月30通程度で、上限に収まる見込み（上限の数は実装時に確認する）。

## 8. 開発ステップ（最小構成から）

1. **Notion の準備**: レシピ_DB に列を追加し、手間・一品完結の値を入れる。買うだけ・切るだけの副菜の行を追加する。献立ログ_DB を作る。
2. **提案ロジック単体**: Notion から読んで、コンディションと気分を引数に提案を出すところまでを、CLI と単体テストで確認する（LINE なし）。
3. **Claude での最終選択**: 理由文付きの選択、自由文の読み替え、失敗時のランダム選択。
4. **LINE Webhook**: ngrok でローカルにつなぎ、ボタン式の会話フローを動かす。
5. **献立ログと「作った？」**: [これにする]で記録、`followup.py` で送信、[作った]で日付を更新する。作ったことないレシピなら「どうだった？」で評価を更新する。
6. **デプロイ**: Webhookサーバーを公開し、GitHub Actions の cron を設定する。
7. **README と記事**: 使い方、スクリーンショット、学びをまとめる。
